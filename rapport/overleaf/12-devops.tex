\chapter{DevOps et mise en production}

\begin{chapterintro}
Ce chapitre clôt la démarche projet en présentant le volet \textbf{DevOps}
mis en place sur SolarEase. L'objectif est de passer d'un code applicatif
fonctionnel à une plateforme \textit{déployable, observable, sécurisée et
maintenable} en production. Le chapitre couvre successivement la
containerisation des microservices backend, le pipeline CI/CD GitHub Actions,
la stack d'observabilité (Prometheus, Grafana, Loki), la qualité de code
(JaCoCo, Trivy), l'infrastructure en tant que code (Kubernetes + Kustomize)
et enfin la stratégie de déploiement multi-environnements. Le frontend
React/Vite reste un projet léger, déployé directement sur \textbf{Vercel}
via le fichier \texttt{vercel.json}~; il n'est donc pas couvert par les
sous-sections DevOps ci-dessous.
\end{chapterintro}

\section{Démarche et architecture DevOps cible}
% ══════════════════════════════════════════════════════════

\subsection{Principes retenus}

La démarche DevOps appliquée à SolarEase s'appuie sur les cinq piliers du
modèle \textbf{CALMS}~: \textit{Culture}, \textit{Automation},
\textit{Lean}, \textit{Measurement}, \textit{Sharing}. Concrètement, cela
se traduit dans le projet par~:

\begin{itemize}
  \item \textbf{Automatisation} -- chaque \textit{push} sur le backend
        déclenche une vérification automatique (build + tests + scans)
        sans intervention humaine~;
  \item \textbf{Reproductibilité} -- les environnements (local, staging,
        production) sont décrits sous forme de code (Docker, Kustomize)~;
  \item \textbf{Observabilité} -- chaque service expose des
        métriques Prometheus et ses logs sont agrégés dans Loki~;
  \item \textbf{Sécurité \og shift-left \fg{}} -- les secrets sont sortis
        du dépôt, les scans Trivy et Gitleaks s'exécutent à chaque PR~;
  \item \textbf{Livraison continue} -- les branches \texttt{develop} et
        les tags \texttt{v*.*.*} déclenchent automatiquement des
        déploiements backend sur Railway, tandis que le frontend est
        livré en continu via Vercel.
\end{itemize}

\section{Containerisation}
% ══════════════════════════════════════════════════════════

\subsection{Stratégie multi-stage}

Chaque microservice backend est packagé via un \texttt{Dockerfile}
\textbf{multi-stage}~: une étape de build Maven (\texttt{maven:3.9.6-eclipse-temurin-17})
produit le jar exécutable, puis une étape \textit{runtime} basée sur
\texttt{eclipse-temurin:17-jre-alpine} embarque uniquement l'artifact final.
Cette approche~:

\begin{itemize}
  \item réduit la taille des images (d'environ \textbf{600~Mo}
        en single-stage à \textbf{180~Mo} en multi-stage)~;
  \item supprime les dépendances de build de l'image finale, ce qui
        réduit la surface d'attaque~;
  \item bénéficie du \textit{layer caching} pour des rebuilds rapides.
\end{itemize}

\begin{lstlisting}[caption={\texttt{backend/identity-service/Dockerfile} --- Multi-stage Maven $\rightarrow$ JRE},
                   label=lst:dockerfile-backend, language=bash]
# Build stage
FROM maven:3.9.6-eclipse-temurin-17 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -Dmaven.test.skip=true

# Run stage
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8081
ENTRYPOINT ["java", "-jar", "app.jar"]
\end{lstlisting}

\subsection{Topologie du \texttt{docker-compose} unifié}

backend (bases de données + microservices + Ollama + n8n) sur un réseau
\texttt{solarease-net} dédié. Tous les secrets sont injectés via un fichier
\texttt{.env} (template fourni dans \texttt{backend/.env.example}). Le
frontend Vite est démarré séparément (\texttt{npm run dev}) en

\subsection{Workflow CI backend -- exécution en matrice}

\begin{lstlisting}[caption={\texttt{.github/workflows/backend-ci.yml} (extrait)},
                   label=lst:backend-ci, language=yaml]
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service:
          - gateway-service
          - identity-service
          - project-service
          - dimensioning-service
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: "17"
          distribution: temurin
          cache: maven
      - run: mvn -B -ntp verify
        working-directory: backend/${{ matrix.service }}
      - uses: actions/upload-artifact@v4
        with:
          name: jacoco-${{ matrix.service }}
          path: backend/${{ matrix.service }}/target/site/jacoco/
\end{lstlisting}

\section{Observabilité (Prometheus + Grafana + Loki)}
% ══════════════════════════════════════════════════════════

\subsection{Exposition des métriques applicatives}

Chaque microservice intègre la dépendance
\texttt{spring-boot-starter-actuator} ainsi que
\texttt{micrometer-registry-prometheus}. La configuration suivante est
ajoutée à chaque \texttt{application.properties}~:

\begin{lstlisting}[caption={Configuration Actuator commune aux 4 services},
                   label=lst:actuator-config, language=bash]
management.endpoints.web.exposure.include=health,info,metrics,prometheus
management.endpoint.health.show-details=always
management.endpoint.health.probes.enabled=true
management.health.livenessstate.enabled=true
management.health.readinessstate.enabled=true
management.metrics.tags.application=${spring.application.name}
management.prometheus.metrics.export.enabled=true
\end{lstlisting}

\noindent Chaque service expose ainsi~:

\begin{itemize}
  \item \texttt{/actuator/health} -- état global (UP / DOWN)~;
  \item \texttt{/actuator/health/liveness} -- sonde \textit{liveness} K8s~;
  \item \texttt{/actuator/health/readiness} -- sonde \textit{readiness} K8s~;
  \item \texttt{/actuator/prometheus} -- métriques au format Prometheus
        (latence HTTP, mémoire JVM, GC, threads, requêtes par endpoint).
\end{itemize}

\subsection{Stack déployée via Docker Compose}

Le fichier

\textit{composable} avec le compose principal~: il ajoute Prometheus,

\section{Qualité et sécurité du code}
% ══════════════════════════════════════════════════════════

\subsection{Couverture de tests backend -- JaCoCo}

Le plugin \texttt{jacoco-maven-plugin} (version 0.8.12) est ajouté aux 4
\texttt{pom.xml} avec deux exécutions~: \texttt{prepare-agent} (au démarrage
des tests) et \texttt{report} (à la phase \texttt{verify}). Le service
\texttt{identity-service} ajoute également une règle de qualité (\textit{quality gate})
avec un seuil minimal de 30~\% de lignes couvertes.

\subsection{Scans de sécurité}

Trois scans automatisés s'exécutent dans le workflow
\texttt{security-scan.yml}~:

\begin{itemize}
  \item \textbf{Trivy filesystem} -- détecte les vulnérabilités dans les
        dépendances Maven et npm (sévérités \texttt{CRITICAL} et \texttt{HIGH})~;
  \item \textbf{Trivy image} -- scanne les images Docker construites avant
        publication~;
  \item \textbf{Gitleaks} -- recherche tout secret accidentellement commité
        dans l'historique Git.
\end{itemize}

Les résultats sont remontés au format \texttt{SARIF} dans l'onglet
\textit{Security} de GitHub.

\subsection{Gestion des secrets}

Tous les secrets ont été extraits du dépôt~:

\begin{itemize}
  \item En local~: fichier \texttt{backend/.env} (gitignoré), template
        public dans \texttt{backend/.env.example}~;
  \item En CI~: secrets GitHub (\texttt{RAILWAY\_TOKEN},
        \texttt{RAILWAY\_PROD\_TOKEN}, etc.)~;
  \item En Kubernetes~: objet \texttt{Secret} \texttt{solarease-secrets}
        injecté par variables d'environnement, dont le \textit{template}
        figure dans \texttt{k8s/base/secret.template.yaml}.
\end{itemize}

\section{Infrastructure as Code (Kubernetes + Kustomize)}
% ══════════════════════════════════════════════════════════

\subsection{Organisation des manifests}

Le dossier \texttt{k8s/} suit le pattern \textbf{base + overlays}
de Kustomize~:

\begin{lstlisting}[caption={Arborescence du dossier \texttt{k8s/}},
                   label=lst:k8s-tree, language=bash]
k8s/
  base/
    namespace.yaml
    configmap.yaml            # variables non sensibles
    secret.template.yaml      # template (à remplir hors Git)
    postgres-identity.yaml    # StatefulSet + Service + PVC
    postgres-project.yaml
    postgres-dimensioning.yaml
    ollama.yaml
    identity-service.yaml     # Deployment + Service
    project-service.yaml
    dimensioning-service.yaml
    gateway-service.yaml
    ingress.yaml              # /api et /ws -> gateway
    kustomization.yaml
  overlays/
    dev/  kustomization.yaml  # 1 replica, demo-seed=true
    prod/ kustomization.yaml  # 2-3 replicas, ddl-auto=validate
\end{lstlisting}

\subsection{Sondes Actuator et limites de ressources}

Chaque \texttt{Deployment} déclare trois sondes pointant sur les endpoints
Actuator, ce qui rend les rollouts \textbf{sûrs} (pas de trafic vers un
pod non prêt) et l'auto-réparation \textbf{automatique}~:

\begin{lstlisting}[caption={Sondes Actuator dans un Deployment K8s (extrait)},
                   label=lst:k8s-probes, language=yaml]
startupProbe:
  httpGet: { path: /actuator/health, port: 8081 }
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8081 }
  initialDelaySeconds: 10
  periodSeconds: 10
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8081 }
  initialDelaySeconds: 30
  periodSeconds: 30
resources:
  requests: { cpu: 200m, memory: 384Mi }
  limits:   { cpu: 1000m, memory: 768Mi }
\end{lstlisting}

\subsection{Routage Ingress}

Un \texttt{Ingress nginx} unique expose le backend sur un domaine~:

\begin{itemize}
  \item \texttt{/api} $\rightarrow$ \texttt{gateway-service:8080}
  \item \texttt{/ws} $\rightarrow$ \texttt{gateway-service:8080} (WebSocket activé)
\end{itemize}

\noindent Le frontend, hébergé sur Vercel, consomme l'Ingress via la
variable d'environnement \texttt{VITE\_API\_BASE\_URL} qui pointe vers le
domaine du backend.

\subsection{Overlays dev / prod}

Les \textit{overlays} appliquent des \textit{patches JSON} sur la base
commune~:

\begin{itemize}
  \item \textbf{dev}~: 1 replica par service, \texttt{SOLAREASE\_DEMO\_SEED=true},
        \texttt{ddl-auto=update}, namespace \texttt{solarease-dev}~;
  \item \textbf{prod}~: 2 à 3 replicas, \texttt{SOLAREASE\_DEMO\_SEED=false},
        \texttt{ddl-auto=validate} (migrations Flyway uniquement),
        namespace \texttt{solarease-prod}.
\end{itemize}

Application en une commande~: \texttt{kubectl apply -k k8s/overlays/prod}.

\subsection{Procédure de release}

\begin{lstlisting}[caption={Procédure standard de mise en production},
                   label=lst:release-flow, language=bash]
git checkout main
git pull --ff-only
git merge --no-ff develop
git tag -a v1.2.0 -m "Release 1.2.0 - Field tracking + RAG"
git push origin main --tags
# -> deploy.yml se declenche automatiquement
# -> images Docker poussees sur GHCR
# -> services deployes sur Railway production
# -> GitHub Release creee avec les notes
\end{lstlisting}

\subsection{Procédure de rollback}

En cas de régression, le rollback s'effectue en une commande Railway
(redéploiement d'une version précédente) ou via Kubernetes
(\texttt{kubectl rollout undo deployment/<svc> -n solarease-prod}).
L'ensemble des procédures opérationnelles (rollback, hotfix, rotation
de secrets, backup PostgreSQL, redémarrage Ollama) est documenté dans le
fichier \texttt{RUNBOOK.md} à la racine du dépôt.

\begin{conclusionbox}
La mise en place de la chaîne DevOps a transformé SolarEase d'un assemblage
de microservices en une plateforme \textit{déployable, observable et
sécurisée}. Les automatisations CI/CD garantissent un retour rapide sur
chaque modification, l'observabilité offre une vue temps-réel sur la
santé du système, l'IaC rend les environnements reproductibles, et la
stratégie GitFlow + Railway permet des livraisons fréquentes en toute
confiance. Les perspectives ouvertes par cette base technique incluent
la mise en place de tests \textit{end-to-end} automatisés (Playwright),
l'ajout d'un \textit{service mesh} (Istio ou Linkerd) pour la
résilience inter-services, et l'intégration d'un système d'alerting
(Alertmanager + Slack) sur les métriques critiques.
\end{conclusionbox}
